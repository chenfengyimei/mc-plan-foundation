# 积分与生成额度

## 模型

Core 维护全局积分账本和每日权益，业务服务不能直接修改余额。

- `EntitlementPolicy`：每日免费次数、时区、适用模块和生效期。
- `EntitlementGrant`：某日或活动授予的不可转移额度。
- `CreditAccount`：用户可消费积分账户。
- `CreditLedgerEntry`：不可变的发放、消费、退款或调整记录。

## 首发规则

- 已验证用户每天获得三个 Skin 创作会话，按 `Asia/Shanghai` 自然日重置，不累计。
- 每个会话默认最多三次实际出图；超过限制需要新会话。
- 免费额度耗尽后可用积分兑换额外会话。
- 注册、每日签到和经过验证的社区贡献可以发放积分。
- 除每日三个免费会话外，奖励值和兑换价格都是带生效期的后台配置，不写死在客户端。

## 账本不变量

- 余额只能由账本记录推导或与其核对，禁止无记录更新。
- 每次变化包含唯一幂等键、来源、原因、操作主体、前后余额和关联业务 ID。
- 重试相同幂等键返回原结果，不重复扣减或奖励。
- 余额不足时整体失败，不产生负余额；人工调整必须记录管理员原因。
- Community 只能提交贡献事件，由 Core 规则决定是否奖励，避免业务服务自行铸造积分。

## 幂等与并发事务

- 每个可重试命令保存调用方、操作名、幂等键、规范化请求指纹、状态和最终结果；同键同指纹返回原结果，同键不同指纹返回冲突。
- 额度按 `(user_id, policy_id, policy_date)` 唯一，`policy_date` 由注入时钟按 `Asia/Shanghai` 计算。并发领取或消费通过数据库唯一约束、行锁或等价原子条件更新保证不超发。
- 积分账户变化在一个 Core PostgreSQL 事务中锁定账户、验证非负余额、追加账本、更新可核对余额投影、写审计与 outbox。事务外不得发布成功事件。
- 免费额度与积分回退由一个消费编排器选择且只成功一种来源；失败重试不能先扣额度再扣积分。外部业务失败后的退款使用新的幂等补偿命令和原消费引用，不修改原账本。
- Redis 锁、队列 exactly-once 假设或进程内互斥不能替代数据库约束。账本核对作业必须能从不可变记录发现并告警投影差异。

奖励值、兑换价格和生效期由版本化策略配置决定。策略变更只影响其生效时间之后的新命令，不追溯改写旧账本或当日已经确定的授予记录。
