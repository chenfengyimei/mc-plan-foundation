# F1 架构评审与门槛关闭检查表

用途：评审代理使用本表形成可审计证据。它不是预先通过的结论；每一项必须引用当前仓库文件、验证输出或新建 ADR。

## 评审对象

- Foundation：宪法、系统架构、数据流、身份、积分、安全、隐私、部署、路线图、风险和已接受 ADR。
- Contracts：Core OpenAPI、公共 Schema、事件信封、版本策略和兼容矩阵；评审阶段只读，需修改时另开 Contracts 主工作流。
- Core：README、AGENTS、状态和开发计划；评审阶段只读。
- Ops：身份与 Core 的真实运行输入、隔离、健康检查、恢复和可观测性要求；评审阶段只读。

## 必须回答

1. Core、Keycloak、Contracts 和 Ops 的责任边界是否唯一，是否存在密码归属、业务身份或审计数据重叠。
2. `issuer + subject` 到 MC Plan 用户 ID 的映射、邮箱验证、停用、重新绑定和身份提供者替换边界是否清楚。
3. Identity/Profile、Developer App/Scope/PAT、Entitlement/Credits、Audit/Outbox 的模块顺序、依赖方向和事务边界是否可以在模块化单体中实现。
4. PAT 是否只保存哈希并支持 scope、过期、撤销和审计；浏览器 PKCE 与服务 Client Credentials 是否分离。
5. 积分账本、每日额度、幂等键、余额前后值、时区重置和并发一致性是否有单一权威语义。
6. 公共 API、错误、分页、幂等、事件和 SDK 的所有者与 Contracts 先行顺序是否明确；是否仍有被实现文档暗示但未进入契约的字段。
7. PostgreSQL、Redis、对象存储、事务发件箱和审计数据的隔离、迁移、回退、保留与恢复责任是否明确。
8. 健康检查、结构化日志、OpenTelemetry、指标、限流、秘密注入和备份恢复是否具有可验证入口，而不是伪造配置。
9. Core 第一条最小纵向链路、测试层级、验收命令和失败回退是否足够具体，可供另一会话直接创建工程骨架。
10. 是否仍有会改变产品范围、许可、隐私、预算或外部账户的重大待决事项；每项必须有 Owner 和决策门槛。

## 允许的评审修改

- 修正 Foundation 内部矛盾、缺失边界、ADR、风险、路线、验收标准和组合状态。
- 创建清楚的后续 Contracts 或 Core 工作流范围。
- 不得在 Foundation 工作流修改产品 OpenAPI、Schema、事件、SDK 或业务代码。

## 通过条件

- 十项问题均有文件证据，且无互相矛盾的权威说明。
- 需要的持久决策已进入 ADR；需要的公共契约修改已拆成 Contracts 主工作流。
- 所有验证实际通过，待决事项都有 Owner 与关闭条件。
- 项目所有者的启动提示词包含明确授权，且工作流记录保存该授权和评审证据。
- 更新 `memory/current/direction.json`、组合状态及相关状态页，使“计划中/活动中”与真实门槛一致。

通过后才可关闭评审工作流并顺序启动 Core 工作流；未通过时记录具体阻塞，不得用“文档已存在”代替结论。
