# ADR-0008：业务身份生命周期与身份提供者迁移

状态：Accepted

日期：2026-10-01

## 背景

ADR-0003 已决定由 Keycloak 管理凭证、由 Core 管理业务身份，但没有完整规定邮箱验证、账号停用、身份重绑和替换身份提供者时的安全边界。若仅依赖邮箱相等或静默修改 `(issuer, subject)`，可能错误合并账号、绕过停用或破坏跨服务稳定 ID。

## 决策

1. Keycloak 是密码、邮箱验证状态、认证会话、MFA 和令牌撤销的权威；Core 不保存密码，也不把邮箱作为跨服务标识。
2. Core 以规范化 `issuer` 与不可解释的 `subject` 组成外部身份唯一键，并映射到稳定的 MC Plan 用户 ID。该映射只允许通过显式、审计的生命周期操作变化。
3. 首次建立映射前，Core 必须验证 token 的签名、issuer、audience、expiry，并要求受信任 issuer 提供已验证邮箱声明；Core 只保存完成业务规则所需的验证结果与时间，不复制邮箱作为身份键。
4. Keycloak 停用或撤销负责阻止新认证；Core 另有业务账号状态并在每个受保护入口执行。暂停、关闭或安全冻结不得只依赖尚未过期的 access token。高风险操作可要求重新认证或查询受控的账号状态。
5. 身份重绑、添加第二身份、账号合并和恢复访问都必须要求当前身份重新认证或经过人工核验的恢复流程；绝不只凭相同邮箱自动重绑。变更写入不可变审计，撤销旧会话，并保留防止旧身份被立即重新占用的安全记录。
6. 替换身份提供者采用显式迁移：先配置受信任 issuer allowlist 与双验证窗口，再通过受审计的映射迁移把新 `(issuer, subject)` 关联到原 MC Plan 用户 ID，验证后撤销旧 issuer。业务表和跨服务引用不改主键。
7. 身份事件、管理 API、错误码或对外账号状态一旦需要跨仓使用，必须先进入 Contracts；Core 私有状态机不能被其他服务通过数据库读取。

## 后果

- Core 需要唯一约束、幂等首次登录、账号状态检查、审计与会话撤销适配边界。
- Keycloak 数据库和 Core 数据库继续隔离；恢复演练必须验证 realm、签名材料、Core 映射和撤销记录的一致性。
- 首个工程骨架只建立验证端口与数据约束，不提前实现账号合并、人工恢复或公开管理接口。

## 变更条件

只有法律合规、地区可用性或已验证的恢复体验要求证明该流程不可用时，才能用新 ADR 替换；替代方案仍必须保持 MC Plan 用户 ID 稳定、防止邮箱自动合并并提供可审计迁移。
