# ADR-0011：事件投递传输形态采用消费者拉取（HTTP）

状态：Accepted
日期：2026-10-06

## 背景

`MCP-F1-CORE-006` 按所有者裁决实现了事务 outbox 发布器与事件恢复，但刻意不绑定传输：生产默认不绑定任何 sink（`OUTBOX_SINK=null`），任何记录不会因占位投递被标记 PUBLISHED。该切片把"事件投递传输形态（broker / HTTP-push / 消费者拉取）"记录为真实投递与消费者切片的精确前置。`MCP-F1-CORE-007` 关闭后，这是 F1 队列上的下一项。

项目所有者于 2026-10-06 会话内明确决策：采用**消费者拉取（HTTP）**；broker 与 HTTP-push 被拒绝。

## 决策

Core 以内部 HTTP 接口暴露事件投递面，消费者用服务凭证主动拉取：

- **拉取与确认**：消费者以稳定游标（基于事件顺序）分页拉取已发布事件，处理成功后显式确认；未确认的事件保持可重投，投递语义为 at-least-once。消费者必须按 `event_id` 幂等（CORE-006 已用测试消费者证明该模型可行）。
- **可见性边界**：投递接口仅面向授权服务消费者（client_credentials 服务客户端 + 专用最小 scope），不经公共浏览器面；事件可见性与 outbox 的 INTERNAL 语义一致，具体路由、scope 命名、确认语义、游标与分页形状由 Contracts 下一预发布版本（alpha.5）先行锁定。
- **无新中间件**：F1 不引入 broker 或推送基础设施；readiness 不因投递面改变（仍仅 PostgreSQL+迁移）。

## 被拒的替代形态

- **HTTP-push（Webhook）**：需要 Core 能访问每个消费者的回调端点，重试/死信与回调管理复杂；本地 Skin/Community 消费者并不持有可被 Core 访问的端点，F1/F3 场景不成立。
- **消息 broker（Redis Streams/Kafka/NATS）**：扩展性最好，但引入新的运行依赖与运维面，且 Q-014（托管数据层）未决；在单一 Core 生产者、少数内部消费者的当前规模下，其收益不抵成本。

## 后果

- Contracts 的下一预发布版本先锁定消费者拉取的公共语义（路径、游标、确认、错误码、事件信封、服务 scope），随后 Core 实现真实投递面（outbox 发布器接入拉取式 sink/投递查询）与第一个真实消费者。
- at-least-once 与 `event_id` 幂等继续是消费者侧的强制契约；重复投递必须由消费者去重。
- 若未来出现跨进程规模（多生产者、外部第三方订阅、高吞吐扇出），需以新 ADR 显式升级为 broker 或推送形态，不得静默替换。

## 变更条件

规模证据（消费者数量、吞吐、投递延迟要求）或外部集成需求出现时重开本决策；在此之前不得在本形态之外增加投递路径。
